# Realty 2.0.0

A leasehold landlord or a freehold authority can now be a player, a Treasury account, or a permission group. This release changes the database, the settings, some commands, the plugin API and the REST API. Read "Upgrade" first.

## Upgrade

The plugin, its modules and `realty-rest` must be upgraded together. `realty-rest` 2.0.0 refuses to start against a database schema other than version 19. The plugin moves the database to version 19 the first time it starts.

Do the steps in this order. Each step is one action.

1. Stop `realty-rest`. A running 1.x `realty-rest` reads columns that the migration removes.
2. Stop the game server.
3. Back up the Realty database. Take the backup now, with both servers stopped, so that it holds the last state: a player action after the backup would be lost from Realty on a restore, while Treasury would keep the payment. The migration changes the schema in several steps, and MariaDB cannot undo a step once it has run. If the migration stops part-way, the way back is to restore this backup and start again from step 4.
4. Replace the Realty plugin jar with its 2.0.0 version.
5. Replace every module jar in `plugins/Realty/modules` with its 2.0.0 version. An old `query-service` module cannot name accounts: the REST API then shows every account without its name, and logs nothing about it.
6. Keep players out until step 12 with the whitelist:
   - If your server does not use a whitelist, set `white-list=true` in `server.properties`.
   - If your server already uses a whitelist, copy `whitelist.json` to a safe place, so that you know who is on it. Then remove everyone except your admins from `whitelist.json`.
7. Start the game server. The migration runs during startup. When it has finished, the log shows `Applied migration V19: parties`. If the log shows an error from the migration instead, stop the server, restore the backup from step 3, and put the old jars back. Find the cause of the error before you start again from step 4.
8. Replace `realty-rest` with its 2.0.0 version and start it. Do this only after step 7 has finished: `realty-rest` 2.0.0 refuses to start until the migration has run.
9. For each legacy government UUID, run the manual fix below. See "Manual fix for a legacy government UUID".
10. Run `/realty group map` for every permission group that should become a party.
11. Change the default parties in `settings.yml`. See "Upgrade: settings".
12. Let players back in:
    - If you turned the whitelist on in step 6, turn it off with `/whitelist off`.
    - If your server already used a whitelist, put back the copy of `whitelist.json` from step 6. Then run `/whitelist reload`.

The whitelist keeps player-triggered payments from reaching the personal account of a legacy UUID between step 7 and step 9. A scheduled termination refund can still fire in that window. It is then paid out of the legacy personal account. Correct it with a manual Treasury transfer.

The first start in step 7 logs an error for each default party that cannot be found. This is expected when your government account is not named `GovSecurity`. Until you finish step 11, `/realty create` and `/realty register` refuse to run without `--landlord` or `--authority`.

### Manual fix for a legacy government UUID

Before 2.0.0, a government landlord or authority was stored as a player UUID that stood for the government account. The migration keeps each such UUID as a player party. The manual fix gives the government account its own party and moves every contract and history entry of the legacy UUID to it.

#### Find the values

You need two values for each legacy UUID: the UUID itself, and the id of the government account in Treasury.

The legacy UUIDs are the values of the old settings `default-freehold-authority-uuid` and `default-leasehold-authority-uuid` in `settings.yml`. Realty 2.0.0 no longer reads these settings, but it leaves them in the file. To find other UUIDs that stood for an account, run this query. It lists the players that are landlord or authority of the most contracts:

```sql
SELECT p.playerUuid,
       (SELECT COUNT(*) FROM LeaseholdContract lc WHERE lc.landlordPartyId = p.partyId) AS leaseholds,
       (SELECT COUNT(*) FROM FreeholdContract fc WHERE fc.authorityPartyId = p.partyId) AS freeholds
FROM PersonalParty p
HAVING leaseholds + freeholds > 0
ORDER BY leaseholds + freeholds DESC
LIMIT 20;
```

To find the id of a government account, run `/gov account list` in the game. Each line shows the id, the name and the balance, for example `3. GovSecurity - $1,000.00`. The id is the number before the dot. You can also read it from Treasury's database: `SELECT account_id, display_name FROM accounts WHERE account_type = 'GOVERNMENT';`.

#### Run the fix

The script below creates the party of the government account, if there is none yet, and moves every contract and history entry of the legacy UUID to that party. It runs in one transaction.

Run it once for each legacy UUID. Each time:

1. Check the account id against `/gov account list`. The script accepts any number; see "A wrong account id" below.
2. Open a new `mariadb` session for each run. Values from an earlier run stay in a session, and a line that fails would use them.
3. Replace `<accountId>` with the id of the government account. Change nothing else.
4. Replace `<legacy uuid>` with the legacy UUID. Change nothing else.
5. Run the whole script, from `START TRANSACTION` to `COMMIT`.
6. Read the two values it shows, as described below the script.
7. Close the session.

```sql
START TRANSACTION;
-- Clears the values of an earlier run, so that a line that fails below leaves its value empty.
SET @account = NULL, @legacy = NULL, @new = NULL, @old = NULL;
SET @account = <accountId>;
SET @legacy = '<legacy uuid>';
SET @old = (SELECT partyId FROM PersonalParty WHERE playerUuid = @legacy);
SET @new = (SELECT partyId FROM AccountParty WHERE accountId = @account);
-- The account's party is created only when the legacy UUID is known and the account has no party yet:
-- first its base row, then its account row with the id the base row got.
INSERT INTO Party (kind) SELECT 'ACCOUNT' FROM DUAL WHERE @old IS NOT NULL AND @new IS NULL AND @account IS NOT NULL;
INSERT INTO AccountParty (partyId, accountId, accountKind)
    SELECT LAST_INSERT_ID(), @account, 'GOVERNMENT' FROM DUAL WHERE @old IS NOT NULL AND @new IS NULL AND @account IS NOT NULL;
SET @new = (SELECT partyId FROM AccountParty WHERE accountId = @account AND accountKind = 'GOVERNMENT');
-- Both must be numbers. If one is NULL, type ROLLBACK and check the values.
SELECT @new AS newParty, @old AS oldParty,
       IF(@new IS NULL OR @old IS NULL, 'CHECK THE VALUES: nothing is moved', 'ok') AS result;
UPDATE LeaseholdContract SET landlordPartyId  = @new WHERE landlordPartyId  = @old AND @new IS NOT NULL;
UPDATE LeaseholdHistory  SET landlordPartyId  = @new WHERE landlordPartyId  = @old AND @new IS NOT NULL;
UPDATE FreeholdContract  SET authorityPartyId = @new WHERE authorityPartyId = @old AND @new IS NOT NULL;
UPDATE FreeholdHistory   SET authorityPartyId = @new WHERE authorityPartyId = @old AND @new IS NOT NULL;
COMMIT;
```

The script shows two values before it moves anything:

- `newParty` is the party of the government account.
- `oldParty` is the party of the legacy UUID.

Both must be numbers, and `result` must say `ok`. Then each `UPDATE` reports how many rows it moved.

If one value is `NULL`, the script moves nothing, and the database is left as it was. If the account id line failed, nothing is inserted either. `result` then says `CHECK THE VALUES: nothing is moved`. If you run the statements one at a time, type `ROLLBACK` at this point instead of going on. Then read the two values together:

- Both are `NULL`: the UUID was not found. It is mistyped, or no contract or history entry ever named it. Check the UUID and run the script again.
- Only `oldParty` is `NULL`: the UUID was not found either. `newParty` is set because the account already has its party, for example from a run for another legacy UUID. Check the UUID and run the script again.
- Only `newParty` is `NULL`: the account is already stored under another kind. See "A party stored under the wrong kind" under "Changes in behaviour". The same happens when the line with the account id failed, for example because `<accountId>` was left in; then check that line.
- Both are numbers and `result` says `ok`: the fix ran.

If every `UPDATE` reports 0 rows, this UUID was already fixed, or it names nothing. Running the script again for the same UUID changes nothing.

#### A wrong account id

The script cannot check that the account id is the government account's. It accepts any number, shows `ok`, and moves the rows. After a wrong id:

- If the id is a personal, business or system account, every payment to or from that landlord or authority fails with `Account #N is no longer a government account`. The action is rolled back, so no money moves.
- If no account has the id, every such payment fails with `Account #N no longer exists`, and is rolled back.
- If the id is another government account, payments do not fail: they go to that account.
- Whoever Treasury lists as a member or authorizer of the wrong account acts for that landlord or authority.

There are two ways back. The first is the script below. It moves every contract and history entry of the wrong account to the right one. Use it only if no contract or history entry named the wrong account before you ran the manual fix; otherwise, its own rows would move too. Run it as you ran the manual fix: in a new `mariadb` session, the whole script, with `<wrong accountId>` and `<right accountId>` replaced.

```sql
START TRANSACTION;
-- Clears the values of an earlier run, so that a line that fails below leaves its value empty.
SET @wrongAccount = NULL, @rightAccount = NULL, @wrong = NULL, @right = NULL;
SET @wrongAccount = <wrong accountId>;
SET @rightAccount = <right accountId>;
SET @wrong = (SELECT partyId FROM AccountParty WHERE accountId = @wrongAccount AND accountKind = 'GOVERNMENT');
SET @right = (SELECT partyId FROM AccountParty WHERE accountId = @rightAccount);
-- The right account's party is created only when the wrong one is found and the right one has no party yet:
-- first its base row, then its account row with the id the base row got.
INSERT INTO Party (kind) SELECT 'ACCOUNT' FROM DUAL WHERE @wrong IS NOT NULL AND @right IS NULL AND @rightAccount IS NOT NULL;
INSERT INTO AccountParty (partyId, accountId, accountKind)
    SELECT LAST_INSERT_ID(), @rightAccount, 'GOVERNMENT' FROM DUAL WHERE @wrong IS NOT NULL AND @right IS NULL AND @rightAccount IS NOT NULL;
SET @right = (SELECT partyId FROM AccountParty WHERE accountId = @rightAccount AND accountKind = 'GOVERNMENT');
-- Both must be numbers, and they must differ. If not, type ROLLBACK and check the values.
SELECT @wrong AS wrongParty, @right AS rightParty,
       IF(@wrong IS NULL OR @right IS NULL OR @wrong = @right, 'CHECK THE VALUES: nothing is moved', 'ok') AS result;
UPDATE LeaseholdContract SET landlordPartyId  = @right WHERE landlordPartyId  = @wrong AND @right <> @wrong;
UPDATE LeaseholdHistory  SET landlordPartyId  = @right WHERE landlordPartyId  = @wrong AND @right <> @wrong;
UPDATE FreeholdContract  SET authorityPartyId = @right WHERE authorityPartyId = @wrong AND @right <> @wrong;
UPDATE FreeholdHistory   SET authorityPartyId = @right WHERE authorityPartyId = @wrong AND @right <> @wrong;
COMMIT;
```

Both values must be numbers, and `result` must say `ok`. If `wrongParty` is `NULL`, the wrong id is not stored as a government account: check it. If `rightParty` is `NULL`, the right id is stored under another kind, or its line failed. The wrong account keeps its party; no contract names it any more.

The second way back is to restore the backup from step 3 and do the upgrade again. This loses every change made in Realty since the upgrade, while Treasury keeps every payment made since then.

### Upgrade: settings

Three settings name the default parties. The packaged `settings.yml` shows their syntax:

```yaml
default-freehold-authority: { name: GovSecurity, type: government }
default-leasehold-landlord: { name: GovSecurity, type: government }
# default-freehold-titleholder: { name: Steve }   # players only; leave out for no titleholder
```

- `type` is `government`, `business`, `system` or `group`. Leave `type` out for a player. For a player, `uuid: <uuid>` may be given instead of `name`. A business or system account is named as `#<id>`.
- `default-freehold-authority-uuid` becomes `default-freehold-authority`.
- `default-leasehold-authority-uuid` becomes `default-leasehold-landlord`.
- `default-freehold-titleholder-uuid` becomes `default-freehold-titleholder`. It must name a player.
- The old keys are no longer read. At startup, a warning names each one that is still in the file.
- Realty merges its packaged defaults into an existing `settings.yml`. After the upgrade the file therefore contains `default-freehold-authority` and `default-leasehold-landlord`. Both hold the packaged value: the government account named `GovSecurity`. If your government account has another name, set it.
- A change takes effect after `/realty reload` or a restart.
- Startup logs an error for each default that cannot be found. `/realty create` and `/realty register` then refuse to run without `--landlord` or `--authority`.
- If `default-freehold-titleholder` is set but cannot be found, `/realty create freehold` and `/realty register freehold` refuse to run without `--titleholder`. They no longer create a freehold that nobody holds.
- The all-zeros UUID is no longer a default.

## Breaking changes

1. **The `g:` prefix is removed.** `/realty add` and `/realty remove` no longer accept `g:<group>`. Use `--group`.
2. **The `--player` flag of `/realty list` is removed.** Use `/realty list <name>`. `/realty me` is unchanged.
3. **The permission `realty.command.set.authority.others` is removed.** `/realty set authority` is gated by `realty.command.set.authority` alone. Whoever holds it may set the authority of any plot to any party.
4. **The plugin API has a new major version, 2.0.0.** This covers `realty-paper-api` and `realty-backend-api`.
   - Events, and the results and methods named below, expose a landlord, an authority, a tenant or a titleholder as a `Party`. A tenant and a titleholder are always a player party in this version.
   - Some methods still take or return a player UUID for such a role. They will change in a later version: `RealtyPaperApi.rent`, `unrent`, `extend`, `payBid`, `payOffer`, `listInboundOffers` and `quickCreateSubregion`, and the `RealtyBackend` result records that `RealtyPaperApi` returns unchanged: `ProposeModificationResult.Success`, `ResolveModificationResult.Success`, `CancelTerminationResult.Success`, `OfferResult.Success` and `WithdrawOfferResult.Success`.
   - The old `get…Id()` getters are deprecated. They return the UUID for a player and `null` for any other party. They will be removed in 3.0.0.
   - These result records now carry a `Party` in place of a UUID: `BuyResult.Success.previousTitleHolder`, `PayBidResult.FullyPaid.previousTitleHolder`, `PayOfferResult.FullyPaid.previousTitleHolder`, `SetTitleHolderResult.Success.previousTitleHolder`, `SetTenantResult.Success.previousTenant` and `TerminateResult.Success.tenant`.
   - `setTenant`, `setTitleHolder`, `transferTitleHolder`, `createFreehold` and `registerFreehold` take the tenant or titleholder as a `Party`. A party that is not a player fails the returned future with an `IllegalArgumentException`. The forms that take a UUID are deprecated and will be removed in 3.0.0. A call that passes a bare `null` must now say which form it means, for example `setTenant(region, (Party) null)`.
   - Methods that took an actor's UUID and a bypass flag now take an `ActorContext`. Build it with `RealtyPaperApi.actorContext`, which asks Treasury and the permission plugin which parties the player acts for. `ActorContext.player` knows no account and no group.
5. **The REST `id` of a party has a wider meaning.** It is a UUID only when `kind` is `personal`. For an account it is the account id. For a group it is the group name. After the manual fix, the existing contracts and history entries of a legacy government UUID carry the account's id.
   - Read `kind` first. Parse `id` as a UUID only when `kind` is `personal`.
   - The OpenAPI schema `PlayerRef` is renamed to `PartyRef`. Code generated from the OpenAPI document must be generated again.
6. **A listing of a party's land has four parts, and `landlord` holds other plots.** This applies to `/realty list`, `/realty me`, `GET /v1/players/regions` and `GET /v1/parties/{kind}/{id}/regions`.
   - The four parts, in this order: `owned` (the party holds the title), `authority` (the party is freehold authority), `landlord` (the party lets the plot as landlord of a lease) and `rented` (the party is tenant).
   - `landlord` now holds the plots the party lets. It no longer holds the plots the party is authority of; those are now in the new part `authority`. A REST client that reads `landlord` gets different plots under the same name, and no error tells it so.
   - In REST, `category` accepts `all`, `owned`, `authority`, `landlord` and `rented`. With `category=all`, one page offset runs over the four parts in that order.
   - In the game, `/realty list` has the categories `owned`, `authority`, `landlord` and `rented`, for example `/realty list landlord GovSecurity --government`.
   - A player whose name is exactly `owned`, `authority`, `landlord` or `rented` cannot be listed by name, because those words are the categories.
7. **`/realty modify price`, `modify duration` and `modify maxextensions` are removed, and players may use `/realty set` on the land they hold.** Permission defaults change with this, and no message at startup tells you so. Read "`/realty set` replaces the `modify` term commands" below before you let players back in.

## `/realty set` replaces the `modify` term commands

### What changes for players

- **`set` does what `modify price`, `modify duration` and `modify maxextensions` did.** The three `modify` commands no longer exist. `/realty modify accept`, `reject`, `withdraw`, `inbox` and `outbox` are unchanged.
- **Who may use `set` and `unset`.** The player must act for the party that holds the region. The database decides who that is:
  - On a lease, it is the landlord.
  - On a freehold with a titleholder, it is the titleholder.
  - On a freehold with no titleholder, it is the authority.
- **On a region that is not rented, the change applies at once.**
- **On a rented region, a change of price, duration or extension limit waits for the tenant's next renewal.** To change a rented region at once, add `--now`. This needs the permission `realty.command.set.now`.
- **A tenant's `set` is a request.** It reaches the landlord's inbox, and the terms change only if the landlord accepts with `/realty modify accept`. This holds even when the tenant also acts for the landlord. Such a tenant can add `--now` to change the terms directly, if they have `realty.command.set.now`.
- **Some changes cannot wait for a renewal.** Without `--now`, a rented region refuses these:
  - `set landlord`, `set tenant`, `set titleholder`, `unset tenant` and `unset titleholder`.
  - `set maxextensions -1` (unlimited).
  - Any change of terms once the lease has been given notice to end.
  - A change of terms from the console, when the landlord is an account or a group.
- `--now` on a region that is not rented is accepted and changes nothing.
- `/realty set authority` is unchanged. It takes no `--now`.

### Check your permissions

Do this before you let players back in. None of these changes is announced at startup.

- **Four permissions now default to true. They defaulted to op.** They are `realty.command.set.price`, `realty.command.set.duration`, `realty.command.set.maxextensions` and `realty.command.unset.price`. Every player can now set the terms of land they hold. To keep these commands for admins only, negate the four permissions for your player groups.
- **`account-managers` decides who holds an account's land.** With `account-managers: members`, which is the default, every member of an account acts for it. If that account is the authority of plots that nobody has bought, every member can now set or clear the price of those plots. If you do not want that, negate `realty.command.set.price` and `realty.command.unset.price` for those players, or set `account-managers: authorizers`. That setting also changes who acts for accounts everywhere else in Realty. It does not change permission groups: every player in a group that is an authority can set or clear the price of the group's unsold plots, and only negating the two permissions stops that.
- **Three permissions are removed.** They are `realty.command.modify.price`, `realty.command.modify.duration` and `realty.command.modify.maxextensions`. If you negated one of them to stop tenants from asking for new terms, that protection is gone. Negate `realty.command.set.price`, `realty.command.set.duration` or `realty.command.set.maxextensions` instead. A grant of a removed permission does nothing and can be deleted.
- **The `.leasehold` permissions are removed.** They are `realty.command.set.price.leasehold`, `realty.command.set.duration.leasehold` and `realty.command.set.maxextensions.leasehold`. Realty checked them before 2.0.0 but never declared them. A grant does nothing and can be deleted.
- **New permission `realty.command.set.now`. It defaults to op.** It allows `--now` on every `/realty set` and `/realty unset` command that takes it. Without it, `--now` on a rented region is refused. The console can always use `--now`.
- **A `.others` permission no longer skips the tenant's wait.** `realty.command.set.<command>.others` and `realty.command.unset.<command>.others` now mean one thing: the player may act on a region they do not hold. A group that has such a permission no longer changes a rented region at once. Give that group `realty.command.set.now` as well, and tell its members to add `--now`.
- **`realty.command.modify.others` covers only `accept`, `reject` and `withdraw`.** To schedule a change on a rented lease of another landlord, a player now needs `realty.command.set.price.others`, `realty.command.set.duration.others` or `realty.command.set.maxextensions.others`.
- **A WorldGuard owner that was added by hand no longer holds a freehold.** `set` and `unset` no longer read the WorldGuard owner list. A player who is an owner in WorldGuard but is not the titleholder in Realty is refused. Make them the titleholder with `/realty set titleholder`, or give them the `.others` permission of the command.

### Check `messages.yml`

- New message keys are added to an existing `messages.yml` automatically.
- **The list `help.management` is not updated.** Realty only adds keys that are missing, and your file already has this list. It still shows the line `/realty modify price|duration|maxextensions`, which no longer works, and it does not show `--now`. Replace the list with the one in `plugins/Realty/defaults/default-messages.yml`. Realty rewrites that file at every start.
- The keys `set.occupied-use-modify`, `set.leasehold-no-permission` and `modify.not-occupied` are no longer used. They can be deleted.

### For plugin developers

- **New overloads take an `ActorContext`.** `setPrice`, `unsetPrice`, `setDuration`, `setMaxRenewals`, `setTenant`, `setTitleHolder` and `setLandlord` on `RealtyPaperApi` have a form that takes who is acting. All except `unsetPrice` and `setTitleHolder` also take `vacantOnly`, which makes a rented lease refuse the change. The old forms still compile. They act as the console does: no check of who is acting, and a rented lease is changed.
- **Result types have new variants. A `switch` over one of them that has no `default` no longer compiles.**
  - `NotAuthorized` is new on `RealtyBackend.SetPriceResult`, `UnsetPriceResult`, `SetDurationResult`, `SetMaxRenewalsResult`, `SetTitleHolderResult` and `SetTenantResult`, and on `RealtyPaperApi.SetTitleHolderResult` and `SetTenantResult`.
  - `Occupied` is new on `RealtyBackend.SetPriceResult`, `SetDurationResult`, `SetMaxRenewalsResult`, `SetTenantResult` and `SetLandlordResult`, and on `RealtyPaperApi.SetTenantResult` and `SetLandlordResult`.
- **The futures of `setPrice`, `unsetPrice`, `setDuration` and `setMaxRenewals` complete on the main thread.** This holds for the old forms too. They completed on the database thread. Do not call `join()` or `get()` on one of them from the main thread: the server would hang. Use `thenAccept` or a similar callback.
- **These methods now redraw the region's loaded signs** after a change that succeeded.
- **`buy`, and the seven setters above, wait their turn on a region.** While a purchase or a rental of a region is being paid for, a call for the same region starts only when that payment has succeeded or has been rolled back.
- **`PriceSetEvent` fires in two more cases:** before a change of price is scheduled for the next renewal, and before a tenant's request for a new price is sent to the landlord. In both cases the price has not changed when the event fires, and it may never change. The event now fires only after Realty has checked that the sender may act.

## What is new

### Parties

- A leasehold landlord and a freehold authority can be a player, a Treasury account (business, government or system), or a permission group that is mapped to a Treasury account. Titleholders and tenants are still players.
- Money moves only through the account that the party names. Realty no longer prefers a player's government account over their personal account.
- A notice for an account reaches its members and authorizers, including offline ones. Which of them is set by `account-managers`. A notice for a group reaches its members who are online.

### Commands

- A plain name is a player. One of `--government`, `--business`, `--system` or `--group` changes what the name means. Examples:
  - `/realty set landlord GovSecurity --government`
  - `/realty set landlord Acme myregion --business`
  - `/realty create leasehold … --landlord police --group`
- A government account is found by name. A business or system account is found by name among the sender's own accounts, or by `#<id>`.
- New commands:
  - `/realty group map <group> <account> --government|--business|--system`
  - `/realty group unmap <group>`
  - `/realty group list`
- `/realty list [owned|authority|landlord|rented] [name] [type flag]` lists the land of any party.

### Settings and permissions

- New setting `account-managers: members | authorizers`. The default is `members`. It decides who acts for an account: members and authorizers, or authorizers only.
- New permission `realty.command.group`. It defaults to op.
- New permission `realty.bypass.conflict-of-interest`. It defaults to op.

### Conflict of interest

Whoever acts for an account or group cannot buy, bid on, make offers on, or be agent for land whose authority is that account or group. The permission `realty.bypass.conflict-of-interest` lifts this rule. Dealing with oneself stays refused.

### REST API

- Every party field is a `PartyRef` with `kind`, `id` and `name`.
- New route: `GET /v1/parties/{kind}/{id}/regions`.
- The explorer shows a party that is not a player as plain text with its kind, for example `GovSecurity (government)`. It has no link.

## Changes in behaviour

- **A type flag comes last.** The form is `/realty set landlord <name> [region] [type flag]`. A flag before the region is refused.
- **Setting a landlord.** A player who is not an admin can give a lease only to a party they act for. A player landlord can therefore no longer hand a lease to another player with `/realty set landlord`. An admin with `realty.command.set.landlord.others` still can.
- **`create` and `register`.** They check no party membership. Whoever holds the permission can name any account or group that resolves. These permissions default to op.
- **Accounts that cannot hold a role.** An account cannot be a landlord, an authority or a group's account if it is archived, requires authorization for every transfer, or is a personal account. If an account becomes archived, or starts to require authorization, later, payments to and from it fail with a clear message. The action is rolled back.
- **`/realty group unmap`.** It is refused while any contract or any history entry names the group. A group that has held a role can be mapped to another account, but it cannot be unmapped.
- **History.** An entry with no tenant or no buyer shows `N/A` there. Realty no longer records the landlord or the authority in that place. Entries written before the upgrade are not changed. In REST the field is left out.
- **Sign profiles.**
  - A name on a sign is always shown as plain text.
  - A placeholder inside the argument of a formatting tag on a sign line is no longer filled in, except inside `hover`, whose text is filled as before. An example is `<click:run_command:'/x <region>'>`, which now runs `/x <region>`. Use `right-click-commands` and `left-click-commands` for commands. No packaged profile is affected.
  - Every other placeholder is filled as before, including one whose key is not a valid tag name, such as `<Price>`.
- **`/realty list`.** A player whose name is exactly `owned`, `authority`, `landlord` or `rented` cannot be listed by name, because those words are the categories.
- **Treasury and LuckPerms.** Realty sees the direct members and authorizers of an account. It does not see members or authorizers that Treasury grants through a LuckPerms group.
- **Without Treasury.** Only players can be parties, and every type flag is refused. Group parties also need Vault's permission service.
- **A party stored under the wrong kind.** Realty stores each account with the kind that Treasury gives it: government, business or system. The manual fix always stores the account as `GOVERNMENT`. If you ran it for an account that Treasury holds as a business or system account, every later use of that account fails with an error such as `account #42 is stored as GOVERNMENT, not BUSINESS`. To correct the row, set the kind that Treasury shows for the account, with its id in place of `42`:

  ```sql
  UPDATE AccountParty SET accountKind = 'BUSINESS' WHERE accountId = 42;
  ```
