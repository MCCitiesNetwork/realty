# Realty 2.4.0

Landlords can now delete, rename and reshape the subregions they carved out with the wand, and admins can rename and reshape any registered region. Signs and flags now update as soon as a region's terms, roles or auction change, so a greeting no longer shows an old price. This release changes the database, and on its first start it permanently deletes leftover rows. Back up the database first. The plugin and `realty-rest` must be upgraded together.

## Upgrade

`realty-rest` 2.4.0 refuses to start against a database schema other than version 24. The plugin moves the database from version 21 to version 24 the first time it starts.

1. **Back up the database.** Two of the migrations delete rows, and the deletion cannot be undone:
   - V23 deletes every lease and freehold contract row that no longer belongs to a region. Earlier versions of `/realty delete` left these rows behind when they removed a region. Nothing reads them.
   - V24 deletes every region tag whose region name is not registered with Realty.
2. Stop `realty-rest`.
3. Replace the Realty plugin jar with its 2.4.0 version and restart the game server. When the migrations have finished, the log shows `Applied migration V22: lease delete when vacant`, `Applied migration V23: contract region cascade` and `Applied migration V24: region tag world`.
4. Replace `realty-rest` with its 2.4.0 version and start it. Do this only after step 3.
5. If you use the PlayerNotifications module, replace it with its 2.4.0 version, so the new notifications get their titles and sort into the right categories. The other modules can stay on 2.0.
6. If landlords should use the new commands, grant them the permissions. Every new permission defaults to op. A server that gives landlords the subregion wand will usually grant `realty.command.subregion.delete`, `realty.command.subregion.redefine` and `realty.command.rename` with it.

### Check `messages.yml`

New message keys are added to your `messages.yml` automatically. No existing key changed its text, so a customised `messages.yml` needs nothing from you. The new keys are:

- `rename.*` and `redefine.*`, the replies to the new commands.
- `subregion.delete.*`, the replies to `/realty subregion delete`.
- `terminate.cancel-delete-mark`, added to the reply when cancelling a termination also cancels a scheduled delete.
- `tag.add-not-registered`.
- Four notifications:

| Key | Sent to | When |
|---|---|---|
| `notification.termination-subregion-removed` | Tenant | Their rented subregion will be deleted when the lease ends |
| `notification.subregion-deleted` | Landlord | A scheduled delete has removed the subregion |
| `notification.region-renamed` | Tenant | The region they rent was renamed |
| `notification.region-redefined` | Tenant or titleholder | The region's shape changed |

The lists under `help` do not show the new commands.

## Deleting a subregion

A manager of a subregion's landlord can delete it with `/realty subregion delete <region>`. A subregion is a leasehold whose WorldGuard parent is a registered freehold, which is what the subregion wand makes. A standalone leasehold made with `/realty create leasehold` can still only be removed with `/realty delete`.

- The first run says what will happen and shows a link that confirms it. Nothing changes until the player clicks it or runs the command again with `--confirm`.
- **A vacant subregion is deleted at once**, with its WorldGuard region.
- **A rented subregion is deleted when its lease ends.** If the lease is not already ending, the command starts an ordinary landlord termination, with the usual notice period (`lease-termination-notice-seconds`). If the lease is already ending, its date stands. Either way the lease is marked for deletion and closed to new tenants. The tenant is told.
- Once the tenant has gone, the scheduler deletes the subregion within a minute and notifies the landlord.
- `/realty subregion delete cancel <region>` removes the mark and opens the plot to tenants again. The termination still stands; the reply links `/realty terminate cancel`.
- `/realty terminate cancel` also removes the mark, so a plot is never deleted later without warning.
- The command is for players. The console uses `/realty delete`.

A region named `cancel` cannot be deleted with this command.

## Renaming a region

`/realty rename <region> <name>` renames a registered region and keeps everything attached to it: contracts, signs, tags and history.

- A manager of a subregion's landlord can rename that subregion. With `realty.command.rename.others`, or from the console, any registered region can be renamed.
- The name may contain only letters, digits and hyphens, and is stored in lower case. It must not belong to another region in that world.
- A rented region can be renamed. The tenant is told the old and new name. The landlord and titleholder are not.
- A rename is refused while a schematic of the region is being captured.

Be aware:

- **Web links to the old name stop working.** `realty-rest` and the explorer address a region by name, so a link to the old name returns 404.
- **The flag profile is applied again under the new name.** Flags someone set on the region by hand are removed, as already happens on every change of state.
- **A grouped profile that lists the old name stops applying.** Realty does not edit your configuration. The reply warns when this happens, and the region uses the global profile until you update the group.
- **A reused name brings its history.** If the new name belonged to a region deleted earlier, that region's history rows appear under the renamed region.
- Fee and refund records keep the name the region had at the time of the sale.

## Redefining a region

A region's shape can now be changed through Realty, with Realty's rules applied. Before, only WorldGuard's `/rg redefine` could do it, which checked none of them.

- **Landlords use the subregion wand.** Mark the new footprint, then run `/realty subregion redefine <region>`. A height dialog opens, starting at the region's current height, followed by a confirm dialog that shows the old and new size. Without `realty.command.subregion.redefine.others`, only a vacant subregion whose landlord you manage can be redefined.
- **Admins use a WorldEdit selection.** Select the new shape and run `/realty redefine <region>`. This works on any registered region, freeholds included, rented or not. There is no confirmation step: the reply gives the old and new size in blocks, and a mistake is put right by redefining again.

Every redefine, by anyone:

- The selection must be a cuboid or a polygon in the region's world, and must differ from the current shape.
- A subregion must stay inside its parent freehold, must not overlap another subregion, and must have at least `subregion-min-volume` blocks.
- Every subregion of the region must stay inside the new shape.
- It is refused while a schematic of the region is being captured.

The region keeps its owners, members, flags, priority, parent and subregions. Flags set by hand are kept. The tenant, or the titleholder of a freehold, is told the shape changed. The region's captured schematic is deleted, because it shows the old shape; the reply says so. Capture the region again to show a preview on the web explorer.

`/rg redefine` still works and still skips these rules.

## Changes in behaviour

- **Flags and signs update when the values they show change.** A flag such as a greeting can show the price, duration, landlord or authority through placeholders. Before, flags were rewritten only when the region changed state, so they kept the old values. Now flags and signs are redrawn after a change to price, duration or max renewals, a lease extension, a landlord or authority change, an auction starting or being cancelled, and when the scheduler ends a lease or an auction. Because the flag profile is applied again, flags set on the region by hand are removed on each of these changes.
- **Each region's tags are its own.** Tags used to be stored by region name only, so two regions with the same name in different worlds shared their tags. The migration gives each such region its own copy. Tags on a name that no registered region has are deleted.
- **`/realty tag add` refuses a region that is not registered with Realty.**
- **Deleting a region deletes its contract rows.** Lease and freehold rows are now removed with their region, so `/realty delete` no longer leaves them behind.
- **Operations on one region run one at a time.** Realty already ordered commands on the same region. Now the scheduler's lease expiry, termination and subregion sweep, title transfers, region creation and deletion, and auction and offer writes also wait their turn. An operation that waited behind a redefine acts on the region's new shape, and the scheduler follows a region that was renamed while it waited.

### New permissions

All default to op.

| Permission | Command |
|---|---|
| `realty.command.subregion.delete` | `/realty subregion delete`, for a subregion whose landlord you manage |
| `realty.command.subregion.delete.others` | Also for a subregion whose landlord you do not manage |
| `realty.command.rename` | `/realty rename`, for a subregion whose landlord you manage |
| `realty.command.rename.others` | Also for any other registered region |
| `realty.command.subregion.redefine` | `/realty subregion redefine`, for a vacant subregion whose landlord you manage |
| `realty.command.subregion.redefine.others` | Also for any subregion, rented or not |
| `realty.command.redefine` | `/realty redefine`, for any registered region |

### Known limits

- An operation queued behind a rename of the same region reports the region as not registered. Run it again under the new name.
- A change made outside Realty, such as `/rg redefine` or another plugin, while a Realty operation on that region runs is not seen by that operation.
- When the scheduler cannot read the current name of a region whose lease has ended, it settles the lease and pays any refund, but leaves WorldGuard alone. The log names the former tenant, who must be removed from the region by hand.

## For plugin developers

This covers `realty-paper-api` and `realty-backend-api`.

- **Records gained fields, so code that builds or deconstructs them must be rebuilt.** `RealtyBackend.ExpiredLeasehold`, `RealtyBackend.TerminatedLeasehold` and `TerminatedLeaseholdView` gain `int realtyRegionId`. `RealtyBackend.CancelTerminationResult.Success` gains `boolean deleteMarkRemoved`.
- **New methods on `RealtyPaperApi`:** `deleteSubregion` and `cancelSubregionDelete`, `renameRegion`, `redefineRegion`, and `getTagIdsByRegion(regionId, worldId)`. Each returns a new sealed result: `DeleteSubregionResult`, `CancelSubregionDeleteResult`, `RenameRegionResult` and `RedefineRegionResult`.
- **New methods on `RealtyBackend`:** `getWorldGuardRegionId(int realtyRegionId)`, which gives a region's current name by its stable id; `deleteVacantLeasehold`, `markForDeletion`, `unmarkForDeletion` and `deleteMarkedVacantLeaseholds`; `renameRegion` and `renameSubregion`; `deleteSchematic`; and `getTagIdsByRegion(regionId, worldId)`.
- **Deprecated:** `getTagIdsByRegion(String)` on both interfaces. It answers across worlds; use the overload that takes the world.
- **Other additions:** `SignCache.renameRegion`, `RegionProfileService.hasGroupedProfile` and `WorldGuardRegion.isValidName`.
- **New events:** `RegionRenameEvent` (cancellable) and `RegionRenamedEvent`; `RegionRedefineEvent` (cancellable) and `RegionRedefinedEvent`; `ScheduledSubregionDeletedEvent`, fired after the scheduler deletes a subregion marked for deletion. The API fires the rename and redefine events, so a plugin calling `renameRegion` or `redefineRegion` gets them too. A plugin that stores region names should move its records in `RegionRenamedEvent`.
- **`/realty subregion delete` fires `RegionDeleteEvent` and `RegionDeletedEvent`**, as `/realty delete` does. `deleteSubregion` on the API fires neither.
- **A `WorldGuardRegion` held across a redefine is safe to pass to the API.** Each queued operation looks the region up again when its turn comes.
